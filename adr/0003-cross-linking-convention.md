# 3. Cross-linking between docs and blog posts

Date: 2026-09-30

## Status

Accepted

## Context

Docs (tutorials) and blog posts reference one another. The first such link shipped broken: `docs/yocto/debugging_yocto.md` carried a placeholder `[Five things you need to know about working with Yocto](#)` — the `(#)` was never filled in — and there was no agreed way to write these links so they survive to production.

Docusaurus offers two ways to link internally, and they fail differently:

- **Absolute permalink** — `[text](/blog/<slug>)` / `[text](/docs/<section>/<slug>)`. Resolved against the site's route table; a dead one is caught by `onBrokenLinks`, which this site sets to `throw`. Works identically in both directions (blog→docs and docs→blog).
- **Relative source-file link** — `[text](../../blog/<date>/<file>.md)`. Docusaurus rewrites the `.md` path to the target's permalink at build and so auto-follows slug changes. But cross-*plugin* (blog↔docs) resolution is the fragile case, and its failures fall under `onBrokenMarkdownLinks`, which previously was set to `warn` — meaning a broken cross-link could ship to production as a mere warning.

The site already had four absolute-permalink cross-links in the wild, so the convention was partly established but undocumented and unenforced.

A related hazard: a doc's permalink defaults to its **filename** and a post's to its dated folder plus `slug`. So renaming or moving a file silently changes the URL and breaks every inbound absolute link.

Alternatives considered:

1. **Relative `.md` links** (the framework's rename-following default). Rejected: their breakage only *warns*, so a broken cross-plugin link reaches production. The whole requirement here is "the link survives in production."
2. **Absolute permalinks with filename-derived URLs.** Rejected: safe only until the first rename; the URL is an accident of the filename, not a contract.
3. **Absolute permalinks with an explicit `slug:` on every link target** (chosen).

## Decision

Three decisions, taken together.

**Link style: absolute permalinks.** Every doc↔post cross-link is written as an absolute site path — `/blog/<slug>` or `/docs/<section>/<slug>` — never a relative `.md` path. This is symmetric across both contexts and every breakage is caught by the existing `onBrokenLinks: 'throw'`.

**Targets carry an explicit `slug:`.** Any doc or post that is *linked to* pins its permalink with an explicit `slug:` in frontmatter, decoupling the URL from the filename/date. Docs use `slug:` (not `id:`) so the path-based `id` the sidebars couple to — the `autogenerated` Yocto/Linux sidebars and the hand-written `codingSidebar` — keeps working. A file can then be renamed (`git mv`) as a standalone commit without changing its URL or breaking inbound links. Slugs are applied **just-in-time**: a doc gets a `slug:` the moment it becomes a link target, not proactively across the whole tree.

**Enforcement: both broken-link checks throw.** `onBrokenLinks` stays `throw` and `onBrokenMarkdownLinks` is raised from `warn` to `throw`, so no class of broken internal link can reach production — the build refuses to publish.

The first application of this convention: `debugging_yocto.md` gained `slug: how-to-debug-yocto-like-a-pro` and its placeholder link now points at `/blog/five-things-you-need-to-know-about-working-with-yocto`; the post links back to `/docs/yocto/how-to-debug-yocto-like-a-pro`.

## Consequences

- "How do I link a doc and a post?" has one answer: an absolute permalink to the target's explicit slug.
- Renames are safe: because the URL lives in `slug:`, a `git mv` preserves both the URL and git history, and can be done as its own commit after the content changes land.
- No broken internal link — absolute or markdown-relative — can ship, since both checks now fail the build.
- Slugs accumulate lazily, only where an inbound link needs protecting, so the frontmatter churn is limited to actual link targets.
- The convention lives in `adr/`, not `docs/`, because `docs/` is the published content tree.
